# Run-week prompt

Use this when handing a regular-season week to the runner (Claude Code; see `CLAUDE.md`).

```text
Run Week [N].

Use the repository's one-command Run Week workflow in AGENTS.md.
Resolve all internal readiness, migration/reset, background-team input, statbook, standings, snapshot and PR prerequisites yourself.
Do not ask me to edit manifests, run helper scripts, research rosters, touch Railway or perform intermediate setup.

Plan:
[From 2014 Week 6: "my Game Plan page is filled in" (or attach the .md or .txt file with its headings). Before Week 6: paste Stone's weekly plan, or write "use the already-closed ex-ante plan" for an authorized rerun]

Run Week [N] only and stop before Week [N+1].
```

The 2013 Week 1 restart (generation 3 under kernel 2013.4) is closed history: see [career/2013/migrations/week_01_kernel_2013_4_restart.md](../career/2013/migrations/week_01_kernel_2013_4_restart.md) (ledger Entry 35).

A current week needs these inputs from Stone before `python scripts/build_week_inputs.py N --season YEAR` can freeze the slate (from 2014 Week 6 `apply_game_plan.py` writes the first and the last from his Game Plan page; see the order below): the week's plan frozen as `call_sheet.json` at `SeasonPaths(YEAR).call_sheet(N)` (2014: `data/2014/Regular_Season/Games/Week_NN/call_sheet.json`; 2013: `career/2013/regular_season/week_NN_<away>_at_<home>/call_sheet.json`), without which the builder blocks; any open role decision the plan must settle, such as the weekly center evaluation; and the game-day inactives, written to `game_day_inactives` in `SeasonPaths(YEAR).depth_chart` (2014: `data/2014/Team_Operations/Team/Depth_Chart/game_depth_chart.json`; 2013: `career/2013/depth_chart.json`), where a week without a new list reuses the last one. Under kernel 2014.6 the builder reads three parts of the call sheet: `offensive_call_sheet` (required), `decisions` (Stone's standing two-point, kickoff and optional fourth-down blocks; required under 2014.6, which decides two-point tries and onside kicks) and `defensive_call_sheet` (optional, records only). The [games and statistical evidence](update_workflow.md#games-and-their-statistical-evidence) section of the update workflow gives the commands that follow. The private snapshot stays on the last merged canonical state until the public PR is merged; only a merged `main` checkout may advance it.

The [decision queue](../state/decision_queue.json) holds a week until Stone's decisions for it are recorded ([career layer](career_layer.md)). `build_week_inputs.py` and `close_week.py --close` (with or without `--continue`) refuse with exit 1 while an open item names the week or a part of its committed call sheet; the dry run of `close_week.py` lists the same items as notes. Only an item owned by Stone becomes a question for the user. When a week opens, `python scripts/open_game_week.py` opens the `weekly_game_plan` item and the `game_day_inactives` item for the next week in which Jacksonville plays, from the schedule and the standing instructions (the healthy-inactive rule covers the healthy inactives only, so the inactives item records why it is still Stone's in `standing_not_applied`); a bye week gets none, nothing is opened twice and nothing while a game is paused. `render_game_week.py` runs it before the week's first briefing, so the briefing and the desk list them, and validation fails an issued briefing whose week has no game-plan item. Until 2014 Week 5 the closing commit opened them by hand; from Week 6 the applied Game Plan resolves them `by: "user"` with the page as their record, applied once no exam the items wait on is still to come (the inactives item waits on every reassessment and projected return the medical entries name before the game). An open item that still holds a closed week fails validation. Stone's standing fourth-down rule is in force and is frozen into each week's call sheet as its `decisions.fourth_down` block, which the game applies at the actual fourth-down distance and spot; no fourth-down item is opened for a week or carried to the next. Neither the queue nor Document 5 changes while a game is paused.

From 2014 Week 6 the week's result page is the Game Report (`SeasonPaths(YEAR).game_report(N)`, `Game_Report.md` in the week's folder; Weeks 1 to 5 keep `output.md`), written from the [Game Report template](../foundation/templates/regular_season_output_template.md) with its two box-score markers. After the close: bring the roster record up to the game, draw the week's awards (`league_awards.py week N --season YEAR --close`), write the week's in-season roster moves page with its event (below), then run **`python scripts/rebuild_pages.py --season YEAR`**, which fills the Game Report's box score and rebuilds every built page in order (see "Every built page, one command" below). Store the week's highlights and reactive events in the league-results page's data twin (`data/YEAR/Regular_Season/League_Results/week_NN.json`: `games` keyed by event id, `reactive_events`), which the page renders under its game headings; the page itself is never edited by hand, and a rebuild replaces anything written on it. `python scripts/rebuild_pages.py --season YEAR --check` then reports nothing. The [update workflow](update_workflow.md#games-and-their-statistical-evidence) gives the details.

## Every built page, one command

`python scripts/rebuild_pages.py [--season YEAR] [--check]` rebuilds every page a builder owns, each a clean page with no system words, in this order: the standings (`render_standings.py`), the statistics with the statistics and records indexes (`render_season_stats.py`), the team tracker (`render_team_tracker.py`), the award pages from the recorded results (`render_award_pages.py`; nothing is drawn), the player pages, the player ages, the club pages (team, roster, depth chart and its change history), the coach pages, the cap views, each game page's box score where stale (`render_box_score.py`), the game-week pages (each played week's index, then the open week's Game Week Briefing, blank Game Plan and index, `render_game_week.py`), the week pages (the Games and league-results indexes and week pages, the injury report, the medical history's game entry and the incident records, `render_week_pages.py`), the in-season roster moves pages (`render_inseason_rails.py`), the desk with its season summary and the calendar (`render_career_views.py`), the trade index, the preseason statistics and last the annual record (`Record.md`). Each page has exactly one builder; the command only calls them. Write mode writes only what differs, never plays a game, draws an award, moves the clock or settles a decision, and exits 1 naming any page a builder refuses (one that would break the clean-page rule, or the career views while a game is paused). `--check` writes nothing and lists every page that is missing, stale, hand-edited or unclean.

The week's awards are drawn first (`league_awards.py week N --season YEAR --close`, which also renders the announcement pages), and the week's in-season roster moves page is written by the week's batch with its event-record line (`render_inseason_rails.py --season YEAR --week N --write --event JSON`); the rebuild keeps an event line a page already carries and writes a missing page without one. The statistical band audit the runner reads is in the data area: `data/YEAR/Regular_Season/Statistics/records/calibration_audit.md`.

## Generated-data rule

Every club dresses at most 46 players. Jacksonville's inactives are Stone's list in `game_day_inactives` of `SeasonPaths(YEAR).depth_chart`; a background club's are chosen mechanically from the bottom of its depth order (`runtime.week_inputs.game_day_actives`), never from a real historical inactive list, and the weekly gate rejects a TeamInput with more than 46 actives.

The one-command workflow keeps large reconstructed TeamInputs in the gitignored `.sim_cache/` workspace. Jacksonville/protagonist games preserve full snap/stat receipts; ordinary background games preserve `compact_stats` receipts with complete nonzero generated statistics but no background snap ledger. The runner must use these bounded-storage paths automatically rather than failing the task because the generated Git diff is too large.

**Season routing:** use the requested NFL season for YEAR, including January/February postseason games. Weekly input, closure, box-score and league-award commands require `--season YEAR`; readiness defaults to `docs/repository_map.json` active_season and can be checked explicitly with `--season YEAR`. Current record ownership follows that map separately. The 2014 release requirements remain blocking even when legacy readiness flags are VERIFIED.

## The game week from 2014 Week 6: briefing, plan, check, apply, practice week and game day, build, close, report

Every game week runs through three pages in the week's folder (`runtime/decisions.py` names them; `runtime.decisions.week_pages` finds them through the folder map) and these steps, in this order. Opening or building a page never moves the clock or creates an event.

1. **Briefing.** When the week opens (after the previous game closes), `python scripts/render_game_week.py` opens the week's two decision items (`scripts/open_game_week.py`, above), then issues the next Jacksonville game's `Game_Week_Briefing.md`, a blank `Game_Plan.md` and the week index (`README.md`), from stored facts only. The staff read is stored as `staff_read.json` (author, date, text) in the week's data folder (`SeasonPaths(YEAR).week_data(N)`) by whoever prepares the week; until then the briefing says "Staff read to come". Whenever the situation changes (a medical exam, a transaction, a decision settled by someone else), `render_game_week.py --check` says a new briefing is due and `render_game_week.py` issues it, keeping the old one beside it as what he saw (`Game_Week_Briefing_October_5.md`). Each issue is entered in the week's issue record (`briefings.json` beside the staff read: the date, the file and the sha256 of the page as it went out), which owns the issue dates; validation holds every briefing, earlier ones included, to it, so a briefing is never edited by hand. Stone settling the week's own items on his Game Plan is his answer to the briefing, not a change of situation: the briefing is compared as it was before he set them, and a briefing issued later for another reason shows them "Set on your Game Plan". The Game Plan is never rewritten by the builder.
2. **Plan.** Stone fills `Game_Plan.md` in place, or uploads a .md or .txt file with the same headings (`--file PATH` on the check or the apply places it as the page; an upload for a week that is played, paused or already built for the game is refused before anything is written). Any section may say "Same as Week N", which carries that week's frozen choices and its applied inactives. The three decision rules and the inactives may say "Standing rule", which freezes the rule in force exactly: the two-point and kickoff rules from the frozen block their instruction's record points at, the fourth-down rule from the `decisions.fourth_down` block stored once on its instruction in `state/current_job.json` (`block`; a kick is the line of scrimmage plus the bound fourth-down artifact's field-goal snap offset, so the field-goal line is the opponent's 34), with Tice's first call on each matching menu filled from the week's own calls (`prepared_calls: first-call-on-each-matching-menu`, `runtime.game_plan.first_calls`), and the inactives as every player out for the game plus the deepest healthy reserve of each of the five largest healthy position groups. When the week sits more healthy players than five, he writes Standing rule above the table and names the others in it, and the briefing's ask says how many the rule leaves to him; when it sits fewer than five, a tie decides the fifth group or a unit would be short, the check says so and he names them all. The page names the legal choices under each heading: the roster, the active books' words (`runtime/offensive_words.py` holds the offensive book's, `runtime/defensive_calls.py` the defensive book's) and the call sheet's situations.
3. **Check.** `python scripts/check_game_plan.py N --season YEAR` says exactly what is missing or invalid, in football words, and exits 1 until the page is complete. It refuses a week that is played, a game that is paused, and a week whose inputs or results are already built from the applied plan. It checks the inactives (the count, the roster, every player out for the game as the game reads it: his availability note or a closed game's injury inside its projected return; an unreadable note is a problem; when more are out than the count, those players only), the depth changes (a role goes to a player of its group and the starter, kicker and punter head it; the defensive-back seats stay valid), every word of every call against the active offensive playbook (concept, personnel, formation, motion, protection, name and tags), a "Same as Week N" that would carry no rule the game needs (and, with the fourth-down rule in force, none silently), the call sheet under the existing validators and the inputs' policy check, the clean-page rule, a subheading where the readers take none, and a briefing the situation has overtaken. Open items with others and exams still to come are listed as notes. A complete page that has changed since it was applied reports "not yet set" and exits 1 until it is applied again.
4. **Apply, and commit it on its own.** `python scripts/apply_game_plan.py N --season YEAR` runs the check and, while either of the week's items still waits on an exam dated that day or later (its `waits_on`; the inactives item waits on every reassessment and projected return the medical entries name before the game), sets nothing: it prints `GAME PLAN: COMPLETE, NOT YET SET` with the exams, so a list written before them is checked against their results (silence never settles it; the call sheet is never frozen without the settled plan item). Once they are held it writes exactly what the game path reads: the frozen `call_sheet.json` (`SeasonPaths(YEAR).call_sheet(N)`, indent 1, its defensive rows citing the page's own lines), the game depth chart's `game_day_inactives` and any order or role change in both chart copies with one update-log entry (a starter, kicker or punter heads his group; a moved player's stale receiver or defensive-back label is cleared by a dated entry), the week's game-plan and inactives items in the decision queue resolved by the user with the page as their record, and the applied plan record `applied_plan.json` beside the call sheet (the page's and the sheet's digests, the inactives, the depth changes and the chart before them, and the event of the apply, whose event line the week index carries and the annual record lists). A re-apply of a revised page replaces the earlier apply's log entry and record and undoes its depth changes first. It then rebuilds every built page (`rebuild_pages.py`). The page stays as the record of his decision; validation fails while the page or the call sheet differs from what the record froze. **Commit the applied plan (the page, the call sheet, both charts, the update log, the queue, the record and the rebuilt pages) on its own, before the inputs are built**: validation requires the call sheet's freeze commit to come before the commit that adds the game's receipts (`validate_repository.freeze_order_errors`; a sheet committed with the receipts fails as well).
5. **Practice week and game day.** The runner closes the practice week and moves the clock to game day before the build, in one commit: the medical reassessments and clearances of the week as dated entries at the end of the medical history, each with its event line, and the roster record's availability notes; the other clubs' real roster moves up to the slate's cutoff in the in-season rails data, researched in two passes (`build_week_inputs.py` refuses until they reach it); the Game Report opened before the game with its first two sections (the preparation) and two event lines, the week's preparation closed (football, with its closure, through the Saturday) and game day (technical, with its closure, the game date); and Document 5's checkpoint, master date and section 9 (the week's dated events past) moved to the game-day event. The master date line takes one of two forms, so that `runtime/player_bios.master_date`, the validator (`, after` ends the date) and the desk (`after the Week N game` marks the week played) read it alike:
   - on game day, before kickoff: `| Master date/time | October 12, 2014, after the game-day clock advance for Week 6 at Tennessee |`
   - after the game: `| Master date/time | October 12, 2014, after the Week 6 game at Tennessee (the final score) |`
6. **Build inputs.** `python scripts/build_week_inputs.py N --season YEAR`, unchanged: it reads the call sheet and the chart as before. When the week's items waited on exams, the apply comes after the practice-week commit that records them (step 5), and is committed on its own before this build; the build refuses while the items are open.
7. **Close.** `python scripts/close_week.py N --season YEAR --close`, unchanged.
8. **Report.** The Game Report (`Game_Report.md`) takes the place of `output.md` from Week 6; Weeks 1 to 5 keep `output.md` as written. After the rest of it is written, with the game's event line and the master date in its after-the-game form, `python scripts/rebuild_pages.py --season YEAR` fills its box score, rebuilds that week's index to link it, opens the next week's items and issues its briefing (step 1) and rebuilds every other built page. Before that rebuild the close records each new injury's medical communication on the roster record in its one format (`runtime/season_summary.py`), as `python scripts/render_week_pages.py --season YEAR --availability` prints it from the game's record, and whoever writes the week's roundup stores its highlights and reactive events as text in the league-results page's data twin (`data/YEAR/Regular_Season/League_Results/week_NN.json`: `games` keyed by event id, `reactive_events`), which the page renders; the page is never edited by hand.

Repository validation checks every week whose folder holds a game week page, played weeks included: its index current, each briefing as its issue record holds it, the staff read well formed and, while the week is open, its Game Plan beside the briefing and its game-plan item in the queue (`render_game_week.validation_errors`, `apply_game_plan.validation_errors`), and every applied week's page and call sheet against its record. The round trip is proved by `tests/test_game_plan.py`: Week 5's frozen call sheet and inactives, written as a Game Plan page and applied in a temporary copy, give a byte-identical Week 5 `call_sheet.json` and the same inactives. It proves the page's football content and the record writer (`build_sheet`, `apply_records`): its frame (the event, the provenance, the decision blocks' ids and the defensive rows' packet lines) is read back from the frozen sheet with `frame_from_sheet`, and Week 5's own text is not a clean page, so the check (`check`) and the frame a Week 6 page writes (`page_frame`) are proved by the check and apply tests instead. The close is proved by `tests/test_week_close_pages.py` and `tests/test_2014_week6_league_pages.py`: a synthetic first Game Report week in a temporary copy, rebuilt by `rebuild_pages.py`, leaves every page clean and adds no validation error.
